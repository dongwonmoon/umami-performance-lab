# 목록의 순서는 유지하고, 개수를 셀 때의 정렬만 제거하기

## 한눈에 보기

오픈소스 웹 분석 도구 **Umami**의 방문자 목록 조회를 분석해,
개수 계산에 불필요하게 포함된 정렬을 분리했다.
고정된 합성 데이터의 로컬 production-build 비교에서 **181일 조회의
API 응답 시간을 931.3 → 550.2ms, 약 41% 줄였다.**

- **형태:** 개인 성능·운영 연구 프로젝트. AI 코딩 에이전트와 협업해 코드 조사,
  구현 및 검증을 진행하고, 실험 범위·해석·채택 여부를 논의했다.
- **기술:** TypeScript, PostgreSQL, Prisma, Docker, Vitest
- **작업 시점:** 2026년 9월
- **기여 상태:** [Umami PR #4523](https://github.com/umami-software/umami/pull/4523)
  제출. **2026-09-09 확인 기준 Open, 미병합.** 운영 환경에 배포한 성과는 아니다.

## 1. 무엇을 해결하려 했나

Umami 운영자는 방문자 목록에서 선택한 기간의 방문 내역을 확인한다.
이 화면은 최근 방문순으로 정렬된 목록뿐 아니라, 페이지 이동에 필요한
개수 정보도 요청한다. 기존에는 비용을 제한하기 위해 개수를 최대 10,000개까지
계산하는 장치가 이미 있었다.

코드를 따라가며 발견한 의문은 단순했다.
**“화면에 보여줄 목록은 정렬해야 하지만, 개수만 구하는 작업도 정렬해야 할까?”**

실제 고객 장애 제보에서 시작한 작업은 아니다. 사용 흐름과 코드를 분석한 뒤,
그 의문이 측정 가능한 비용으로 이어지는지 로컬 환경에서 확인했다.

## 2. 원인: 목록용 SQL이 개수 계산에도 사용됐다

방문자 목록 함수는 최근 방문순 정렬이 포함된 SQL을 공통 페이지 처리 함수에
전달했다. 공통 함수는 이 SQL을 감싸 개수를 계산한 다음, 별도로 목록을 조회했다.
그 결과 **목록에 필요한 정렬이 개수 계산용 서브쿼리에도 남았다.**

181일 범위의 실행 계획에서는 기존 개수 쿼리가 91,225개 그룹을 처리하고
정렬한 뒤 최대 10,000개라는 개수를 반환했다. 개수 경로에서만 정렬을 제거하자,
그 실행 계획에서는 필요한 그룹 수에 도달한 뒤 더 일찍 멈출 수 있었다.
개수 쿼리 단독 중앙값은 약 542 → 56ms로 줄었다.

다만 이것을 그대로 사용자 체감 개선이라고 발표하지 않았다.
**개수 계산이 빨라져도 실제 목록 조회 비용은 남으므로**, 다음 검증은
개별 SQL이 아니라 완성된 API 응답을 대상으로 진행했다.

## 3. 변경: 필요한 곳에만 정렬을 남겼다

| 처리 | 기존 | 변경 후 |
|---|---|---|
| 개수 계산 | 목록용 정렬까지 포함 | 정렬 없이 기존 상한 유지 |
| 실제 목록 조회 | 최근 방문순 정렬 | 기존 정렬 그대로 유지 |
| 필터·페이지 이동·응답 형식 | 기존 계약 | 변경하지 않음 |

공통 페이지 처리 함수에 **목록 조회에만 적용하는 기본 정렬 인자**를 추가하고,
방문자 목록 호출자가 기존 정렬식을 그 인자로 전달하도록 했다.
기존 호출자는 새 인자를 생략하면 원래 동작을 유지한다.

새 인자는 소스 코드가 정한 SQL 표현식이지 사용자가 전달하는 정렬 문자열이
아니다. 외부 정렬 기능이나 캐시, 인덱스, 별도 서비스는 추가하지 않았다.
ClickHouse 경로와 다른 보고서의 SQL도 수정하지 않았다.

검토 과정에서 다음 대안은 피했다.

- **SQL 문자열에서 정렬을 일괄 제거:** 내부 집계나 윈도 함수에 필요한 정렬까지
  건드릴 수 있어 채택하지 않았다.
- **단순한 고유 방문자 ID 개수로 대체:** 기존 그룹에는 호스트명도 포함돼 있어
  결과 의미가 달라질 수 있었다.
- **필터에 기본 정렬값 삽입:** 쿼리만 바뀌는 것이 아니라 응답 메타데이터까지
  달라질 수 있어, 목록 전용 인자로 분리했다.

대신 공통 함수가 인자 하나를 더 갖게 되는 유지보수 비용은 생겼다.
적용 위치를 제한하고 기존 호출 방식의 회귀 테스트를 남기는 것으로 관리했다.

## 4. 검증: 빠른 것보다 먼저, 같은 결과인지 확인했다

빈 결과, 개수 상한 전후, 필터·검색, 두 번째 페이지, 같은 시각의 방문과
여러 호스트를 가진 세션을 확인했다. SQL 실험에 그치지 않고 실제 수정된 함수와
PostgreSQL을 연결해 개수·목록·페이지 정보·응답 메타데이터를 비교했다.

이후 같은 데이터와 요청을 사용하는 수정 전후 앱을 각각 빌드했다.
워밍업 후 실행 순서를 AB/BA/AB로 바꾸어 API 시간과 DB CPU 사용량을 측정했다.
각 측정 응답은 고정된 기준 응답과 전체 JSON이 같은지 검사했다.
동시 요청 4건의 짧은 부하도 별도로 확인했다.

upstream `dev`로 옮긴 패치는 관련 테스트 12개를 통과했고, 별도 환경에서
클린 설치·빌드도 확인했다. 다만 해당 빌드는 DB 검사·마이그레이션을 생략했고
upstream 설정상 타입 검사가 비활성화돼 있었다. 전체 린트의 기존 오류도
수정 전 코드에서 재현됐으며, 이를 숨기거나 관련 없는 수정으로 함께 처리하지 않았다.

## 5. 결과: 긴 기간에서는 개선, 짧은 기간은 유보

PostgreSQL 15 / Umami v3.3.1 기준, 한 사이트의 고정 합성 데이터
262,196개 이벤트·91,225개 세션을 사용했다.

| 조건 | 기존 | 변경 후 | 해석 |
|---|---:|---:|---|
| 7일 API 응답 | 74.9ms | 72.2ms | 뚜렷한 개선 주장 안 함 |
| 30일 API 응답 | 140.5ms | 135.2ms | 뚜렷한 개선 주장 안 함 |
| 181일 API 응답 | 931.3ms | 550.2ms | 약 40.9% 감소 |
| 181일 DB CPU / 요청 | 919.34ms | 530.51ms | 약 42.3% 감소 |
| 181일 동시 4건 전체 완료 | 909.8ms | 535.8ms | 약 41.1% 감소 |

순차 API 시간은 각 3개 요청으로 구성된 블록의 중앙값을 구한 뒤, 3개 블록의
중앙값을 사용했다. 동시 4건 수치는 개별 요청 지연이 아니라 전체 완료 시간이다.
API 시간에는 응답 JSON 해석이 포함된다. CPU는 DB 컨테이너 누적 CPU 시간의
증가량을 완료 요청 수로 나눈 값이며, 두 시간 지표는 같은 의미가 아니다.

세 번의 181일 비교 모두에서 개선됐지만, 변경 후에도 변동은 있었다.
순차 블록 중앙값은 527.3~697.4ms였고, 개별 요청 하나는 810.2ms에 도달했다.
좋은 표본만 골라내지 않았다. 30일 DB CPU는 대표값이 약 0.4% 증가해,
모든 조건에서 빨라졌다고 주장하지 않는다.

## 6. 어디까지 말할 수 있나

이 사례가 보여주는 것은 **실제 사용 경로의 불필요한 작업을 찾아,
기존 동작을 보존하는 변경을 만들고 로컬에서 효과를 검증한 과정**이다.

한 데이터 분포와 소수의 반복으로 얻은 결과이므로 운영 트래픽의 p95,
최대 처리량, 실제 사용자 체감이나 비용 절감을 입증한 것은 아니다.
컨테이너에는 명시적인 CPU·메모리 제한을 두지 않았다.
개수와 목록은 여전히 별도의 순차 조회이므로, 그 사이 데이터가 추가되는
상황의 일관성 문제를 해결했다는 주장도 하지 않는다.

또한 공개 측정 파일에는 모든 측정 응답 본문이 아니라 실행 당시 동일성
검사 결과가 남아 있다. 성능 수치는 v3.3.1의 측정이며,
`dev`용 PR 패치가 같은 비율의 개선을 낸다고 재측정한 것은 아니다.

핵심 배움은 **최적화의 단위를 사용자 응답까지 확장하되, 변경 범위는
문제가 확인된 처리에 한정하는 것**이었다. 개수 쿼리의 약 90% 단축보다,
목록 계약을 유지하면서 API에서 약 41% 단축을 확인한 결과를 대표 성과로 삼았다.
