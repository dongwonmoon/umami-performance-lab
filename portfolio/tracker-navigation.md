# 분석 서버가 느려도 링크 이동까지 기다려야 할까

## 한눈에 보기

Umami의 추적 이벤트가 붙은 동일 창 링크는 분석 요청이 끝나야 페이지를 이동했다.
수집 서버 응답만 늦춰 이 결합을 재현하고, **전송 준비는 기다리되 응답은 기다리지
않는 후보**를 검증했다. 로컬 합성 페이지에서 수행한 2026-09-09 연구이며,
운영 환경 배포나 upstream 제출 성과가 아니다.

TypeScript, Fetch/keepalive, CORS, 브라우저 수명주기와 Node HTTP 수신기를 사용했다.
사용자와 AI 에이전트가 범위·해석을 논의했고 에이전트가 구현·검증을 지원했다.

## 1. 분석 도구가 원래 사이트의 이동을 지연시키는 경로

기존 코드가 모든 링크를 막는 것은 아니다. 추적 이벤트가 지정된 동일 창 링크에서
기본 이동을 취소하고, `trackElement(...).finally(...)`에서 이동을 다시 수행한다.
내부 전송은 `fetch`와 응답 JSON 해석을 기다린다. 따라서 요청이 진행 중이면
사용자의 페이지 이동도 기다린다.

과거의 요청 실패 시 이동 복구 수정은 확인했지만, 응답 대기가 왜 필요한지에 대한
개발자의 의도는 확정하지 않았다. 클릭 이벤트 전달 기회를 보장하려는 선택일 수
있으므로, 단순히 기다림을 없애는 것이 안전한지도 따로 확인했다.

초기 자동화 도구의 실행 시간은 오버헤드가 섞여 버렸다. 대신 같은 페이지의
`performance.now()`로 **클릭부터 pagehide까지**를 측정했다. 목적지 렌더링 시간은 아니다.
응답 지연을 0→1,500ms로 바꾸자 추적 링크 중앙값은 21.0→1,526.3ms가 됐고,
추적하지 않는 링크는 같은 대기 경로를 타지 않았다.

## 2. 첫 번째 안은 빨랐지만 이벤트가 도착하지 않았다

바로 페이지를 이동하는 실험안은 기본 설정에서 빨랐다. 그러나 `beforeSend`가
1초 동안 비동기 전처리를 하는 조건에서는 두 번 모두 관찰 시간 안에 이벤트가
도착하지 않았다. `keepalive`는 아직 시작하지 않은 요청을 대신 실행해주지 않는다.
영구 손실이라고 단정하지는 않았지만, 이 관찰만으로 즉시 이동 안을 기각했다.

| 흐름 | 기다리는 범위 | 판단 |
|---|---|---|
| 기존 | 전처리 → 요청 → 응답 → 이동 | 느린 응답이 이동을 지연 |
| 기각한 안 | 즉시 이동 | 비동기 전처리 중 전달 누락 관찰 |
| 최종 후보 | 전처리 → fetch 호출 → 이동 | 응답 완료와 이동을 분리 |

최종 후보는 기존 keepalive를 사용한다. 공개 `track()`의 응답 대기 동작은 유지하고,
동일 창 링크 경로만 내부 옵션으로 분리했다. 큐·재시도·임의 타임아웃은 추가하지 않았다.

## 3. 이동만 빨라졌는지, 수신도 됐는지 확인

고정 dev `9fb7bace`의 실제 tracker 소스를 사용했다. 로컬 페이지와 수신기의
호스트·포트를 다르게 하고 매 요청에 새로운 CORS 사전 요청을 요구했다.
OPTIONS는 500ms, POST 응답은 1,500ms 늦췄다. 기본·비동기 전처리 조건마다
수정 전후를 두 번 비교했고, 이동 후 3,200ms 동안 실제 HTTP 수신을 확인했다.

| 엔진 | 기본 링크 이동: 기존 → 후보 | 전처리 1초 포함: 기존 → 후보 |
|---|---|---|
| Chromium | 약 2,016–2,028 → 5.6–6.1ms | 약 3,017–3,019 → 1,014–1,015ms |
| Firefox | 2,020–2,026 → 5ms | 3,021–3,022 → 1,017–1,019ms |
| Playwright WebKit | 2,018–2,020 → 5–7ms | 3,015–3,019 → 1,010–1,011ms |

각 엔진의 수정 전후 비교 8개 이벤트가 모두 한 번씩 수신됐다. 작은 표본에서의
관찰이며 전달 성공률 보장이 아니다. WebKit 검사는 실제 Safari 앱·iOS 검사가 아니다.
전처리 취소·예외, 추적 비활성화, 공개 API의 응답 대기, 백그라운드 요청 실패도
검사했고 소스 회귀 검사 6개를 남겼다.

## 4. 얻은 것과 남은 비용

응답 지연이 사용자 이동으로 전파되는 범위를 줄이면서 전처리는 유지했다.
대신 내부 코드가 전송 시작과 응답 완료를 구분해야 한다. 느리거나 끝나지 않는
`beforeSend`는 여전히 이동을 늦춘다.

일반 운영에서 응답이 얼마나 자주 느린지, HTTPS·큰 payload·오래된 브라우저,
실제 Umami DB 저장은 검증하지 않았다. 의도적으로 준 약 2초 지연을 제거한 것이지
일반 사용자의 이동을 항상 2초 단축했다는 결과가 아니다.

### 이력서용 요약

> 분석 요청의 응답 대기가 호스트 페이지 이동에 전파되는 경로를 재현하고,
> 비동기 전처리는 보존한 채 전송 시작과 응답 완료를 분리하는 후보를 구현·검증.
> 로컬 지연 주입 및 3개 브라우저 엔진에서 이동 지연과 HTTP 수신을 함께 확인하고,
> 전달이 관찰되지 않은 즉시 이동 안은 기각했다.
