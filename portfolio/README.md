# Umami 성능·운영 연구 포트폴리오

오픈소스 웹 분석 도구 Umami의 실제 기능 흐름을 분석하고, 로컬 합성 데이터에서
불필요한 작업과 외부 의존성을 확인한 개인 연구 프로젝트다. 새 분석 서비스를
만들거나 실제 고객 장애를 해결한 프로젝트는 아니다.

사용자는 문제 선택·가정·적용 판단을 AI 에이전트와 논의하고 긴 측정을 직접 실행했다.
에이전트는 코드 조사·구현·검증·기록을 지원했다. 아래 결과를 AI 없이 혼자 작성한
코드나 운영 트래픽에서 달성한 성과로 소개하지 않는다.

## 먼저 읽을 사례

| 사례 | 보여주는 판단·기술 | 결과와 경계 |

| [퍼널의 조회 범위 명시](funnel-start-bound.md) | 조건의 논리적 동치, 인덱스 선택, 동시 부하와 CPU | 정확한 7일 API p50 52→23.1ms. 전체 기간에서는 작은 손해 관찰 |

모든 숫자는 각각의 고정 조건에서 나온 값이다. 서로 다른 사례의 수치를 합쳐
서비스 전체 성능 개선율로 계산하지 않는다. 제출·병합·배포 역시 별개다.
방문자 수 사례의 PR 상태는 그 문서에 적힌 확인 시점 기준이며 실시간 상태표가 아니다.

## 나머지 연구도 보존했다

| 연구 | 결과·판단 | 근거 |
|---|---|---|
| Journey 중복 제거 | 194,070행을 검사해도 제거 0행. 181일 API 391.8→286.6ms. 동률의 상위 100개 선택은 달라질 수 있음 | [실험 기록](../experiments/journey-distinct.md) |
| Attribution 공통 집계 | 30일 SQL 프로토타입 first-click 228.4→96.6ms. 실제 소스 이식 후 응답 검증과 API 성능 측정은 구분 | [실험 기록](../experiments/attribution-shared.md) |
| 단건/batch 입력·조회 병행 | 기존 batch의 효용과 관찰 범위 내 저장 결과 확인. 새 최적화나 최대 용량 성과가 아님 | [실험 기록](../experiments/ingestion-batch.md) |
| 후보 탐색·기각 | 문제를 발견하지 못한 관찰도 보존해 같은 조사를 반복하지 않음 | [탐색 기록](../experiments/next-candidates.md) |

## 자료를 읽는 방법

- 이 폴더: 지원서·면접에 사용할 문제, 판단, 결과 설명.
- `experiments/`: 고정 버전, 실험 조건, 실패와 한계의 상세 원장.
- `evidence/`: 공개 가능한 합성 측정 표본과 집계. `patches/`, `scripts/`: 변경과 검사 도구.
- 원본 DB·전체 로그·토큰은 공개하지 않는다. 새 clone만으로 과거 수치를 그대로
  재현할 수 있는 것은 아니며, 각 실험의 입력 준비 조건을 따라야 한다.

### 프로젝트 소개 예시

> Umami를 대상으로 사용자 기능에서 발생하는 DB 작업과 브라우저 비동기 흐름을
> 분석했습니다. 로컬 합성 데이터로 수정 전후의 결과·지연·자원 사용을 비교하고,
> 조건별 개선과 회귀를 구분해 패치와 검증 근거를 남겼습니다. 방문자 수 계산
> 최적화는 upstream PR로 제출했으며, 다른 후보는 로컬 검증 사례로 보존했습니다.
