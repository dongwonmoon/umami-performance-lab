# 퍼널 조회의 시작일 하한을 SQL에 명시하기

오픈소스 웹 분석 도구 **Umami**의 PostgreSQL 퍼널 조회를 따라가며,
후속 단계가 전체 이벤트 테이블을 다시 훑는 조건을 관찰했다. 앞 단계의
시작일과 단계 간 순서에서 따라오는 날짜 하한을 SQL에 한 줄로 명시하고,
결과 동일성과 SQL·HTTP 양쪽 성능을 고정 합성 데이터에서 확인했다.

- **형태:** 개인 성능·운영 연구 프로젝트. AI 코딩 에이전트와 협업해 코드 조사,
  측정 코드 구현 및 검증을 진행했고, 실험 조건·해석·범위를 직접 검토했다.
- **기술·시점:** TypeScript, PostgreSQL, Prisma, Docker, Vitest · 2026년 9월
- **변경 범위:** PostgreSQL 퍼널 분기에 `we.created_at >= {{startDate}}` 추가
- **제외 범위:** 새 인덱스·캐시·DB 설정·ClickHouse 수정 없음

## 1. 목적과 관찰

Umami 사용자는 기간과 단계를 정해 방문 흐름을 확인한다. 이번 작업은
고객 장애를 해결했다는 주장으로 시작한 것이 아니라, 실제 화면 경로에서
짧은 기간의 퍼널 조회가 어떤 일을 하는지 확인하려는 독립 연구였다.
실행 계획에서 정확한 7일 조회의 두 번째 단계는 50,859행을 통과시키고
212,447행을 제거하며 이벤트 테이블을 순차 스캔했다. 후속 이벤트에는 앞
단계 이후라는 순서 조건이 있었지만, 전체 조회 시작일은 직접 표현되지 않았다.

## 2. 원인과 최소 변경

앞 단계가 `startDate` 이후이고 각 후속 단계가 앞 단계 이후라면 후속 이벤트도
`startDate` 이후라는 하한이 논리적으로 따라온다. 이를 명시하면 결과를
바꾸지 않으면서 PostgreSQL이 더 좁은 범위를 선택할 여지가 생긴다고 가정했다.
실제로 추가한 것은 다음 한 줄이다.

```sql
and we.created_at >= {{startDate}}
```

새 인덱스·애플리케이션 캐시·DB 설정은 도입하지 않았다. PostgreSQL 퍼널
분기에만 적용했고 ClickHouse 경로는 그대로 두었다. [재현용 패치](../patches/funnel-start-bound.patch).

## 3. 먼저 결과가 같은지 확인

날짜 경계, 60분 단계 간격, 반복 방문, 동일 시각 이벤트, wildcard, 이벤트 속성
필터와 8단계 퍼널을 검사했다. 수정 전후 API 전체 JSON과 UI의 `Last 7 days`
결과를 비교했다. UI 화면·호출 코드·API 결과를 별도로 교차 확인했으며,
이 기간은 7일 전 자정부터 오늘 마지막 밀리초까지 8개 날짜를 포함한다.

## 4. SQL과 HTTP에서 본 결과

SQL 단독 비교는 준비 호출 후 20회씩 순서를 바꾸어 실행했다. 7일 p50은
40.8→11.5ms, 30일은 68.1→43.8ms, 전체 181일은 192.0→195.0ms였다.
두 번째 단계는 기존 순차 스캔에서 `website_event_created_at_idx`를 사용하는
Index Scan으로 바뀌었다.
같은 upstream Dockerfile로 수정 전후 앱을 빌드하고 동일 DB에 연결해,
로그인 시간을 제외한 localhost HTTP 요청부터 JSON 해석까지 측정했다.
아래 p50은 중앙 두 표본의 평균이 아니라 40개 표본 nearest-rank의 20번째다.

| 범위 | 수정 전 p50 / p95 | 수정 후 p50 / p95 |
|---|---:|---:|
| 정확한 7일 | 52.0 / 60.2ms | 23.1 / 32.3ms |
| 정확한 30일 | 78.6 / 102.6ms | 56.2 / 65.6ms |
| 전체 181일 | 198.8 / 224.8ms | 202.7 / 224.6ms |

짧은 기간에서는 HTTP 응답 시간이 줄었지만 전체 기간은 소폭 늘었다.
특정 짧은 조회 조건의 개선을 모든 기간의 개선으로 일반화하지 않았다.

## 5. 동시 조회에서의 확인

사용자가 실행한 추가 측정은 동시 요청 1·4·8개를 각각 3회 반복한
closed-loop 비교였다. 아래는 전체 요청을 합친 백분위수가 아니라 각 반복
지표 3개의 대표값(중앙값)이다.

| 범위 | 동시 요청 | p50 (ms) | 성공 요청/초 | CPU (ms/요청) |
|---|---:|---:|---:|---:|
| 7일 | 8 | 81.7 → 54.7 | 97.80 → 145.35 | 37.90 → 9.95 |
| 전체 | 8 | 224.4 → 226.6 | 35.15 → 34.91 | 203.38 → 206.82 |

7일 동시 8개에서는 처리량이 97.80→145.35 요청/초로 증가하고 요청당 DB
CPU가 37.90→9.95ms로 감소했다. 전체 기간은 p50·CPU가 소폭 증가했고
처리량도 35.15→34.91로 약간 낮아졌다.

## 6. 어디까지 말할 수 있나

이 사례는 단계 순서에서 보장되는 조건을 SQL에 명시해 기존 결과를 유지한 채
특정 기간 조회의 불필요한 스캔을 줄일 수 있음을 보여준다. Umami v3.3.1,
PostgreSQL 15.19, 고정 로컬 합성 데이터와 준비된 캐시 조건의 결과다.
실제 서비스 트래픽, 운영 장애, 비용 절감, 사용자 체감이나 SLO는 입증하지 않는다.
동시성 측정의 CPU는 DB 컨테이너 전체 누적값이며 쿼리 하나의 CPU가 아니다.
cold cache, 다른 데이터 분포, 수집과 조회의 동시 실행도 확인하지 않았다.
전체 기간의 소폭 회귀를 포함해 모든 입력에서 유리하다고 주장할 근거는 없다.

이 변경은 로컬 실험 저장소에 재현용 패치로 보존했으며, 운영 환경에 배포하거나
Umami upstream에 제출한 결과가 아니다.
