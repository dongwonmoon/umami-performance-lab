# 단일 요청이 빨라져도 병렬화를 기본값으로 채택하지 않은 이유

## 한눈에 보기

Umami 성능 보고서의 반복 집계를 분석해 캐시 분리와 쿼리 병렬화를 비교했다.
병렬화는 로컬 순차 조회를 약 31% 줄였지만, CPU가 제한된 동시 조회에서는
완료 시간이 약 10% 늘었다. **구현 실패가 아니라, 적용 조건을 확인하고 일괄
적용을 보류한 판단 사례**다. 운영 개선을 달성한 대표 성과의 대체물은 아니다.

2026년 9월, Umami v3.3.1·PostgreSQL·Docker 기반 합성 실험이다.
사용자는 AI 에이전트와 조건·해석·판단을 논의하고 긴 측정을 실행했으며,
에이전트가 코드 조사·후보 구현·검증을 지원했다.

## 1. 같은 기간인데 요약을 다시 계산해야 하나

운영자가 성능 보고서에서 지표를 바꿀 때 차트와 전체 지표의 요약 집계를 요청한다.
전체 요약은 선택 지표와 무관하지만, 데이터가 추가되면 값은 달라질 수 있다.
따라서 이를 영원히 같은 값이라고 가정해 캐시하는 것은 올바른 출발점이 아니었다.

두 후보를 비교했다. 하나는 요약 재사용을 위한 요청·캐시 분리이고,
다른 하나는 기존 API를 유지하며 차트와 요약 SQL만 병렬 실행하는 작은 변경이다.
캐시 분리는 지표 전환에서 더 빨랐지만 오류 처리·요청 조율과 요약/상세의
최신성 차이를 관리해야 했다. 병렬화는 그 비용이 작지만 SQL 작업 자체를 없애지 않는다.

## 2. 대기 시간 감소와 작업량 감소를 구분

| 로컬 조건 | 기존 | 병렬화 | 해석 |
|---|---:|---:|---|
| CPU quota 미설정, 순차 요청 중앙값 | 283.3ms | 195.7ms | 약 31% 감소 |
| DB 2 CPU, 순차 요청 중앙값 | 383.7ms | 309.3ms | 약 19% 감소 |
| DB 2 CPU, 동시 요청 4개, 8건 완료 시간 중앙값 | 2.88초 | 3.17초 | 약 10% 증가 |

위 행들은 서로 다른 부하 조건이다. 마지막 행은 개별 요청 지연이 아니라
8건을 마치는 시간이다. 병렬화는 한 요청이 기다리는 시간을 겹칠 수 있지만,
여러 요청이 같은 CPU를 쓰면 자원 경쟁을 늘릴 수 있다. 제한된 동시 부하에서는
요청당 DB CPU도 약 10% 늘었다. 데이터 경쟁에 의한 결과 오류와 자원 경쟁은 구분했다.

가벼운 초당 약 2건 입력과 간헐적 보고서 조회도 확인했다. 측정 이벤트 180건은
모두 저장됐고 그 조건에서 입력 지연 악화가 관측되지 않았다. 그러나 전략별 조회가
10건뿐이므로, 이를 일반적인 설치 환경이나 운영 신뢰성의 증거로 확대하지 않았다.

## 3. 설정을 하나 더 만드는 대신 멈춘 이유

일반적인 Umami 설치의 CPU·동시 사용자 분포를 확정할 근거가 없었다.
어느 쪽이 절대다수라고 추측해 기본값을 바꾸지 않았다. 조건에 따라 켜는 설정도
가능하지만, 실제 배포 요구 없이 설정·검증 조합을 늘릴 이유는 부족했다.

결론은 모든 병렬화를 버리는 것이 아니다. 후보 패치와 불리한 측정을 보존하고,
구체적인 운영 환경이나 upstream 요구가 생기면 적용 여부를 다시 판단하기로 했다.
캐시 분리 역시 채택하지 않았다. 어느 안도 운영 배포하거나 upstream에 제출하지 않았다.

### 이력서·면접용 요약

> 분석 보고서의 캐시 분리·쿼리 병렬화 대안을 구현하고 로컬 합성 데이터에서 비교.
> 순차 조회 약 31% 단축에도 CPU 제한·동시 부하에서는 완료 시간이 약 10% 늘어,
> 무조건 적용을 보류하고 적용 조건과 검증 한계를 기록했다.
