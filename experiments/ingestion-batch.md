# 이벤트 입력: 단건 요청과 기존 batch 비교

상태: 단건/batch 및 입력 병행 관찰 검토 완료(2026-09-07 KST). 이번 조건에서 종결.
upstream 수정이나 성능 개선을 주장하는 실험이 아니다.

## 질문과 범위

같은 합성 페이지뷰를 `/api/send`로 한 건씩 보낼 때와 `/api/batch`로
10/100건씩 묶을 때, 전송 완료 시간·이벤트당 DB CPU·실제 저장 결과가 어떻게 다른가?

공식 [서버 측 이벤트 가이드](https://docs.umami.is/docs/guides/send-server-side-events)는
서버 이벤트 전송과 과거 데이터 입력을 사용 사례로 안내한다.
v3.3.1의 [batch 코드](https://github.com/umami-software/umami/blob/ca661c7057984aa98ed4f7083d84dae2f65bfcb0/src/app/api/batch/route.ts)는
최대 500개 항목을 순서대로 `send.POST`에 전달한다. PostgreSQL
[저장 경로](https://github.com/umami-software/umami/blob/ca661c7057984aa98ed4f7083d84dae2f65bfcb0/src/queries/sql/events/saveEvent.ts)는
이벤트마다 insert한다. 이는 코드 사실이지 병목이나 결함의 증거가 아니다.

가설: 묶음 전송은 HTTP 왕복 비용을 줄여도 이벤트당 DB 작업은 크게 줄이지 않을 수 있다.
첫 측정에서는 HTTP 동시 요청을 1개로 고정한다. 동시성·세션 캐시 유무·조회 부하를
한꺼번에 바꾸지 않는다. batch가 빠르다는 사실만으로 upstream 개선 사례가 되지는 않는다.

## 고정 조건과 판정

- 공식 Umami 3.3.1, PostgreSQL 15의 별도 Compose 환경. 퍼널 패치 미적용.
- 기존 합성 DB dump를 **새 볼륨에 복원**한다. 원래 앱(:3000)/DB는 그대로 둔다.
- Demo SaaS: `18573f23-3e24-44ef-b580-154cf371e7fe`.
- 원본 dump SHA-256: `388bbf3e1ab06a6ae82b7a0d3f8e7b6b530f71400b164ae577092009c8e28c32`.
  이 비공개 로컬 합성 fixture는 공개 배포하지 않는다. 다른 fixture의 수치를 같다고 주장하지 않는다.
- 동일 페이지뷰 내용·고정 timestamp·User-Agent, warmup에서 얻은 동일 세션 cache를 재사용한다.
  블록 구분용 tag만 다르며 토큰은 결과에 저장하지 않는다.
- 본 측정: 모드별 1,000 이벤트, 3회, 순서 순환. 짧은 smoke: 모드별 100 이벤트, 1회.
  각 모드의 warmup은 측정에서 제외한다. 생성한 이벤트는 삭제하지 않고 구분해서 센다.
- 전체 이벤트 묶음의 완료 시간, events/s, ms/event, 요청별 지연, DB 컨테이너 CPU delta를 기록한다.
  100건짜리 요청 지연과 한 건짜리 요청 지연을 같은 작업량의 지연으로 해석하지 않는다.
- HTTP 200뿐 아니라 batch 항목 오류와 DB 저장 수·경로·내용을 확인한다.
  누락/오류/불일치가 있으면 성능 결론을 보류한다. 자동 재시도하지 않는다.

이번에는 warm cache의 단일 세션 페이지뷰만 본다. 새로운 방문자마다의 세션 생성,
커스텀 속성, 서버리스 connection pool, 최대 용량, 장애 시 전달 보장은 검증하지 않는다.
DB CPU에는 background 작업과 측정 경계 비용이 섞일 수 있다. 로컬 HTTP 결과를
원격 클라이언트의 네트워크 지연이나 실제 트래픽으로 일반화하지 않는다.

## 실행

저장소 루트에서 실행한다. **아래 복원은 최초 1회, 비어 있는 새 DB에서만** 한다.
이미 준비된 환경에서는 복원하지 않고 측정 명령만 실행한다.

```sh
docker compose -f compose/ingestion.yml up -d --wait db
docker exec -i umami-ingestion-db-1 pg_restore --exit-on-error --no-owner -U umami -d umami < .local/umami-expanded-20260906.dump
docker compose -f compose/ingestion.yml up -d --wait app

node scripts/ingestion-batch.mjs --check
node scripts/ingestion-batch.mjs --smoke
node scripts/ingestion-batch.mjs
```

본 측정은 사용자가 실행한다. 결과는 `.local/ingestion-batch-*.json`에 저장하며
오류가 나도 부분 결과를 보존한다. 재실행은 새 tag로 이벤트를 추가하므로 초기 DB 크기가
조금씩 달라진다. 반복 순서를 순환하고 시작 상태를 기록하되 완벽히 동일한 DB 복원 비교는 아니다.

측정 후 자원을 멈출 때(데이터 삭제 없음):

```sh
docker compose -f compose/ingestion.yml stop
```

### 본 측정 — 2026-09-07 KST

사용자 실행 결과: `.local/ingestion-batch-2026-09-06T163252234Z.json`.
SHA-256: `5e220c9b61fd00cb1d277d7f98d66f25c8810da9aeef4d200c62086b409117c8`.
이미지는 위 smoke와 같으며, 실행 시간은 UTC 16:32:52~16:33:33이었다.

main이 JSON을 직접 재집계했다. 9블록·9,000개 측정 이벤트에서 HTTP 오류 0,
저장 수·고유/기대 경로·website·제목·타입·timestamp 불일치 0이다.
실제 DB에서도 각 측정 tag 1,000건/고유 경로 1,000개와 각 warmup tag 100건을 확인했다.
최초 cache 획득 1건과 블록 warmup 900건을 포함해 9,901건이 추가됐다.
실험 DB는 263,907→273,808건, 원래 퍼널 DB는 263,306건 그대로다.
단건/10건/100건 묶음의 블록당 측정 요청 수는 각각 1,000/100/10개다.

각 지표는 **세 반복 지표의 중앙값**이다. 요청당 지연이 아니라 동일 1,000건의 완료 시간을 비교한다.

| 방식 | 1,000건 완료 | 처리량(events/s) | DB CPU(ms/event) |
|---|---:|---:|---:|
| 단건 전송 | 4.623초 | 216.31 | 0.440 |
| 10건 묶음 | 2.832초 | 353.15 | 0.400 |
| 100건 묶음 | 3.486초 | 286.89 | 0.478 |

반복 편차를 숨기지 않기 위한 원 수치(각 셀: 완료 시간 초 / DB CPU ms/event):

| 반복 | 단건 | 10건 묶음 | 100건 묶음 |
|---|---:|---:|---:|
| 1 | 4.6230 / 0.463 | 2.8317 / 0.400 | 2.5041 / 0.379 |
| 2 | 5.2239 / 0.440 | 3.5003 / 0.430 | 3.4857 / 0.478 |
| 3 | 4.1119 / 0.421 | 2.6597 / 0.364 | 3.6931 / 0.567 |

**판단.** 10건 묶음은 단건 대비 세 번 모두 빨랐고 대표 완료 시간이 약 39% 짧다.
100건 묶음도 세 번 모두 단건보다 빨랐지만 편차가 크며, 반복 3에서는 10건 묶음보다 느렸다.
따라서 batch 크기 10이 최적이라거나 크게 묶을수록 좋다고 주장하지 않는다.
DB CPU는 10건 묶음에서 소폭 감소했고 100건 묶음에서는 증가한 반복도 있다.
묶음 크기에 비례한 DB 자원 절감은 관찰되지 않았다.

현재 코드는 batch에서도 이벤트별 처리를 수행하므로 HTTP 요청 수 감소의 이득과
항목별 작업의 잔존이라는 설명에 부합한다. 다만 앱 CPU·세부 단계·I/O 대기는 측정하지
않아 절감분을 HTTP 왕복만의 효과로 분해하거나 실제 병목 위치를 확정할 수 없다.
동시 요청 1개인 결과로 서비스 최대 처리량이나 DB 포화를 주장하지 않는다.

기존 batch의 효용을 확인한 기준선으로 기록한다. 이 결과만으로 upstream 변경,
벌크 insert나 큐 도입을 시작하지 않는다. 후속 후보는 입력과 대시보드 조회가 겹칠 때
조회 지연이 달라지는지 관찰하는 것. 아래에서 작은 후속 관찰만 승인했다.

## 후속 관찰: 입력과 통계 조회의 겹침

2026-09-07 KST 사용자 승인, 구현·smoke·사용자 본 측정 및 결과 검토 완료.
**최적화가 아니라 후보를 가려내는 관찰**이다.
동시 수집과 조회는 제품의 정상 사용 흐름이지만, 이 때문에 문제가 빈번하다는 근거는 없다.
공개 [#4494](https://github.com/umami-software/umami/issues/4494)도 서버리스 환경의
연결 한도 보고이며, 이 로컬 환경에서 쓰기/읽기 경쟁을 입증한 사례가 아니다.

기존 환경과 코드에서 다음 한 조건만 바꾼다.

- **조회만 → 입력 병행 → 조회만**: 각 단계에 통계 요약 API 30개 요청.
  조회 응답 후 다음 요청까지 1초 대기한다. 첫 warmup 2회는 제외한다.
- 조회는 `WebsiteMetricsBar`가 사용하는 `/api/websites/:id/stats` 하나다.
  전체 대시보드의 여러 패널, 브라우저 렌더링, 실시간 화면을 재현한다고 주장하지 않는다.
  이 주기는 실험의 샘플 수집 간격이지 실제 UI 자동 새로고침 주기가 아니다.
- 입력 병행 단계에서만 `/api/send` 단건을 보내고 **응답 후 200ms 대기**한다.
  동시에 최대 1개, 최대 5 events/s이며 실제 속도를 기록한다. 재시도·밀린 요청 폭주는 없다.
  실제 이용 빈도에 대한 자료가 없으므로 이 양을 일반적인 트래픽이라고 부르지 않는다.
- 조회는 기존 합성 fixture의 고정 7일(2026-08-31~09-07 KST)이다.
  새 입력 timestamp는 조회 종료 이후로 둔다. 같은 앱/테이블에 쓰되 집계 대상은 바꾸지
  않아 응답 전체가 기존 기준선과 동일한지 확인할 수 있다. 오늘의 집계 값 변화는 범위 밖이다.
- 이전 실험과 동일한 단일 세션 cache·브라우저 UA. 실행별 tag로 합성 입력을 구분한다.
  단계별 조회 지연·오류·응답 일치, 입력 수/실제 속도, DB CPU 총량을 기록한다.
  혼합 단계의 DB CPU에는 쓰기도 포함되므로 조회 한 건의 비용이라고 해석하지 않는다.
- 입력을 멈추고 진행 중 요청까지 끝낸 뒤 저장 수·경로·website·시간을 확인한다.
  검증 SQL은 측정 구간 밖에서 실행한다. 오류 시 나머지 단계를 진행하지 않고 부분 결과를 남긴다.

본 실행은 약 1분 30초 이상이며 사용자가 수행한다. `--smoke`는 단계별 3개 조회와
200ms 조회 간격으로 줄인 동작 확인이다. 속도 결론은 본 실행 결과로만 판단한다.

```sh
node scripts/ingestion-overlap.mjs --check
node scripts/ingestion-overlap.mjs --smoke
node scripts/ingestion-overlap.mjs
```

결과는 `.local/ingestion-overlap-*.json`. 같은 Compose 환경을 재사용하며 DB 복원은 반복하지 않는다.
전후 조회 기준선의 흔들림과 비교해 혼합 단계의 절대 지연·상대 차이를 함께 본다.
30개 표본의 p95는 탐색용이며, 작은 차이를 유의미한 개선 기회로 단정하지 않는다.
차이가 없으면 이 조건에서 종료한다. 차이가 있더라도 원인 확인 없이 수집기/DB를 수정하지 않는다.
문제를 만들기 위해 입력량을 늘리거나 CPU·메모리를 줄이는 후속 실험은 자동으로 진행하지 않는다.

준비 검증: Luna 구현 후 main이 검토하고 `node --check`, `--check`, `--smoke`를 실행했다.
`--check`는 진행 중 입력을 중단 요청한 뒤 끝까지 기다리고 추가 입력하지 않는지 확인한다.
smoke 결과는 `.local/ingestion-overlap-2026-09-06T164922916Z.json` (`status=complete`).
세 단계 각각 조회 3회가 모두 HTTP 200·기준 응답 일치였고, 병행 입력 3/3건이 저장됐다.
DB를 별도로 조회해서도 3건/고유 경로 3개를 확인했다. 캐시 준비용 1건을 포함해
실험 DB는 273,812건, 원래 퍼널 DB는 263,306건 그대로다. `git diff --check`와
결과 파일의 Git 제외도 확인했다. smoke의 지연 수치로 성능 결론을 내리지 않는다.

### 입력 병행 본 측정 결과 — 2026-09-07 KST

사용자 결과: `.local/ingestion-overlap-2026-09-06T180644845Z.json`.
SHA-256: `53a05c0617c37e92ac283b1ab79ab86ea64442c0f3c2906d4fdd6ecd6b02bf17`.
UTC 18:06:45~18:08:17, 공식 앱/DB image ID는 앞선 측정과 같다.

main이 원본 90개 표본에서 nearest-rank p50/p95를 재계산하고 기록값과 대조했다.
90개 조회 모두 HTTP 200·고정 기준 응답 일치이며, 입력 오류도 없다.
혼합 구간에서 138건을 시도해 138건 저장했다(실제 4.56 events/s).
저장 수·고유/기대 경로·website·timestamp가 모두 138건으로 일치하고,
별도 DB 조회에서도 저장 수·고유 경로·website·timestamp를 확인했다.
캐시 준비용 1건을 포함해 실험 DB는 273,812→273,951건,
원래 퍼널 DB는 263,306건 그대로다.

| 단계(각 30회 조회) | p50 | p95 | 단계 DB CPU 총량 |
|---|---:|---:|---:|
| 조회만 — 전 | 42.8ms | 48.9ms | 0.935초 |
| 입력 병행 | 41.8ms | 47.9ms | 1.169초 |
| 조회만 — 후 | 40.9ms | 46.5ms | 0.960초 |

조회 구간은 각각 30.322/30.289/30.276초였으며 혼합 구간의 입력 종료 대기는
추가 5.2ms였다. CPU 구간은 종료 대기까지 포함하며, 혼합 구간에는 쓰기 CPU도 포함된다.

사이에 있고 오류·누락도 없어, 이 경로를 최적화할 근거를 얻지 못했다.
입력 때문에 더 빨라졌다고도 해석하지 않는다. 한 번의 전/중/후 관찰로 영향이 전혀
없음을 증명한 것은 아니며, 전체 대시보드·높은 동시성·다른 입력/조회 분포에는 일반화하지 않는다.
사전에 정한 대로 부하나 자원 제한을 바꿔 조사를 연장하지 않는다. 실제 증상이나
구체적인 다른 운영 요구가 생겼을 때 재검토한다.

결과 원본은 Git 제외 상태로 유지했다. 이번 검토에서 새 측정 실행, 앱/측정 코드 변경,
환경 변경, 커밋/push는 하지 않았다.
